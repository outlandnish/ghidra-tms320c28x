# Contributing to ghidra-tms320c28x

Thanks for wanting to contribute. A few ground rules — most of them are about
keeping the licensing story clean so this module can be freely used, packaged, and
potentially upstreamed.

## Licensing (inbound = outbound)

By submitting a pull request, issue-attached patch, or any other contribution to
this repository, **you agree to license your contribution under the Apache License,
Version 2.0** (see [LICENSE](LICENSE)) — the same license the rest of the project
carries. No separate CLA. This mirrors the model that Ghidra itself uses.

Practically, this means:

- You have the right to license the code you're submitting (you wrote it, or your
  employer has authorized it, etc.).
- You grant the patent license described in Apache-2.0 §3 for your contribution.
- You accept the disclaimer of warranty and limitation of liability.

If you're contributing on behalf of an employer, make sure your employer is OK with
that before opening a PR.

## Do not contribute vendor-derived binary material

To keep this module Apache-2.0-clean and safe to redistribute, PRs **must not**
include:

- Object files, `.lib` archive members, `.out` / COFF binaries, or any content
  extracted from TI runtime libraries (`rts2800*.lib`, `libc_*.lib`, etc.).
- Compiled TI toolchain output (`dis2000` listings, generated `.asm`, etc.) as
  committed test fixtures. Generate these at test time from a locally installed
  TI CGT/C2000Ware — see [tests/run_fw_parity.sh](tests/run_fw_parity.sh) for the
  pattern.
- Firmware images, boot ROMs, or any binary you don't own the rights to redistribute.
- Verbatim prose copied from TI reference manuals (SPRU430F, SPRUHS1C, SPRUHM8K, …).
  Instruction encodings, register addresses, and field names are facts about the
  hardware and are fine. Paraphrase copied sentences and cite the section number.

If a new script needs TI-authored register maps to be useful, extract only the
facts (name + address + field bits) and note the source manual/section in a file
comment. If you copy from a TI-BSD-licensed C header, add the TI copyright + BSD-3
notice per [NOTICE](NOTICE).

## File headers

New source files should start with the short-form SPDX header:

```
// SPDX-License-Identifier: Apache-2.0
// Copyright <year> <your name or handle>
```

Use the comment style native to the file type (`#` for shell/PowerShell/SLEIGH,
XML comment for `.ldefs`/`.pspec`/`.cspec`, `//` for Java/Gradle). For Ghidra
scripts, keep any `//@category` / `//@keybinding` tags inside the leading
contiguous comment block so Ghidra's Script Manager still parses them.

Do not add a header to `data/languages/*.sla` — it's a generated build artifact
and is not tracked.

## The `.sla` is a build artifact

`data/languages/tms320c28x.sla` is generated by the SLEIGH compiler from the
`.sinc` / `.slaspec` sources and is **not** checked into the repo. CI builds it on
every push/PR and publishes it as a release artifact. If your PR touches
`.sinc` / `.slaspec`, do not commit a rebuilt `.sla` — CI will handle it. If you
need to test locally:

```sh
"$GHIDRA_INSTALL_DIR/support/sleigh" data/languages/tms320c28x.slaspec
```

## Testing

See [docs/TESTING.md](docs/TESTING.md) and [tests/run_disasm_test.sh](tests/run_disasm_test.sh).

For spec changes that touch decode behavior, run the firmware parity harness
against a real image (requires a local TI CGT install with `asm2000` / `dis2000`):

```sh
# Linux / macOS
export C2000WARE=/opt/ti/ti-cgt-c2000
export GHIDRA_INSTALL_DIR=/opt/ghidra_12.1.2_PUBLIC
tests/run_fw_parity.sh -Fw <swapped.bin> -Start 0x9af9e -Count 0xf2 -Tag aes
```
```powershell
# Windows
$env:C2000WARE = "C:\path\to\ti-cgt-c2000_..."
pwsh -File tests\run_fw_parity.ps1 -Fw <swapped.bin> -Start 0x9af9e -Count 0xf2 -Tag aes
```

Zero WRONG mnemonics + zero length-skew is required; UNDEFs indicate missing
opcodes and are a follow-up, not a regression.

## Working on several branches at once (git worktrees)

If you keep multiple branches checked out via `git worktree`, use
`scripts/worktree.{sh,ps1}` — it seeds each worktree's per-worktree config
(`.c28x.env`) and warns when two worktrees share one Ghidra install (which can't
run headless tests in parallel, because the processor module is a singleton within
a Ghidra install). See [docs/WORKTREES.md](docs/WORKTREES.md).

## Attribution for outside code

If you merge or adapt code from another Apache-2.0 project (including other Ghidra
processor modules, or [mwdmwd/ghidra-c28x](https://github.com/mwdmwd/ghidra-c28x)):

- Preserve the upstream copyright line in any file that carries their code.
- Add the upstream project to [NOTICE](NOTICE).
- Reference the specific upstream commit hash in your merge commit message so the
  provenance is auditable later.
